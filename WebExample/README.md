# Web Example

This example is the reference embedding pattern for a SwiftTUI `App` in the
browser. It does not use a terminal emulator. The build compiles the app to
WebAssembly. Then `@swifttui/web` mounts the app on a canvas.

## Requirements

- Node.js 18 or later. Any npm setup works; Bun also works.
- [swiftly](https://www.swift.org/swiftly/) with the `swift-6.3.3-RELEASE_wasm`
  Swift SDK. If either is missing, the build stops and prints the install
  command.
- [Binaryen](https://github.com/WebAssembly/binaryen) (`wasm-opt`), optional.
  Without it the build continues and the wasm binary stays larger.

## Run

```bash
npm install        # once, in the repository root
npm run dev        # in WebExample/
```

Then open <http://localhost:3000>.

`dev` builds the Swift WASI artifacts first: `TerminalApp/dist/scene-manifest.json`
and `TerminalApp/dist/assets/app.wasm`. This step is slow on the first run;
the script warns before it starts. Then `dev` serves the page with the
required isolation headers and rebuilds the front-end bundle when files under
`src/` change. There is no hot reload: refresh the page after edits.

`dev` compiles a debug wasm binary, and the configuration applies to the
framework as well as the app: debug compiles fast but runs slower, release
(`npm run build`) compiles slowly but runs at full speed.

## Demonstrates

- `@swifttui/web` provides `createWebHostApp` and
  `createWasmSceneRuntimeFactory`. A small bootstrap mounts a SwiftTUI scene
  on a DOM element without a terminal emulator.
- `@swifttui/build` uses `SwiftTUIWASI` and `WASIRunner` in manifest mode. It
  packages the same `App` declaration as a static manifest and wasm file. Any
  static host can then deploy these files.
- The WASI target reuses `CounterCore.CounterApp`. Thus, the terminal, native
  SwiftUI, and browser hosts run the same app.

## What to copy when adopting this pattern

The minimum a host needs:

1. A WASI build of a SwiftTUI `App` (see `TerminalApp/`).
2. A static manifest the WebHost can read (`scene-manifest.json`, generated by
   `WASIRunner` in manifest mode).
3. A host that serves `Cross-Origin-Opener-Policy: same-origin` and
   `Cross-Origin-Embedder-Policy: require-corp` so `SharedArrayBuffer`-backed
   stdin works.
4. Dependencies on `@swifttui/web` and `@swifttui/build`.
5. The mount sequence from `src/frontend.ts:bootstrap()`: `createWebHostApp` +
   `createWasmSceneRuntimeFactory`.

The other code in `src/frontend.ts` draws page controls and reports state
around a viewport-sized mount. A host page can provide different controls.
Only the `.terminal-host` mount and WebHost bootstrap are required.

## App relationship to counter

`WebExample` imports `CounterCore`. It exposes `CounterApp` through the stable
`WebExampleApp` name. Thus, the terminal, native SwiftUI, and browser hosts
compile the same `CounterView` and `CounterApp` source. The public browser
reference contains one scene.

## Build

This package has three cooperating parts:

- **`TerminalApp/`**: a Swift package with the reusable `WebExampleScenes`
  library. A small `WebExampleApp` executable calls
  `WASIRunner.run(WebExampleApp.self)`.
- **`scripts/`**: the build and serve scripts. They run on Node or Bun.
  `build-terminal.mjs` compiles the wasm and generates the manifest through
  `@swifttui/build`. `build-web.mjs` bundles the front end with esbuild.
  `serve.mjs` serves the result with the isolation headers.
- **`src/`**: the browser front end that mounts `WebHost` with the manifest
  and wasm file.

```bash
npm run build      # dist/ (web bundle) + pages-dist/ (web bundle + TerminalApp/dist)
npm start          # serve a production build on http://localhost:3000
```

The website repository deploys `pages-dist/` under `/webexample/`. The public
site uses it as the live demo in an iframe.

The WASI build flags and the isolation headers are required; [`AGENTS.md`](AGENTS.md)
explains both. The canonical build commands live in
`scripts/build-terminal.mjs` and [`TerminalApp/build.sh`](TerminalApp/build.sh).

## Test

The test runner is Bun:

```bash
bun test                             # unit tests
bun run test:browser                 # Playwright browser-integration specs
```

The browser specifications build the full bundle first, then drive Chromium
and WebKit against the served demo.
